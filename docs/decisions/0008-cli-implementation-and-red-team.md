# 0008: command line interface implementation and red team pass

Status: done.

## Context

The safety core, decisions 0004 through 0007, had no way to be invoked from a terminal. This
entry covers `cmd/wtff` and `internal/cli`: the first commands that make wtff a program a person
can actually run, plus the review pass that followed.

## What was built

`cmd/wtff/main.go`, the entrypoint. It parses nothing itself; it wires the process's real
stdin, stdout, stderr, and exit code to `internal/cli.Run` and does nothing else.

`internal/cli`, three commands:

- `wtff remove [--dry-run] [--purge] [--yes] <path>...` plans and, on confirmation, applies a
  removal of the named paths, staged by default.
- `wtff undo <batch-id>` restores a staged batch.
- `wtff staged` lists batches currently held.

Every command function takes its input and output as explicit parameters, an `io.Reader` for
input and `io.Writer` for output and errors, rather than reading `os.Stdin` and writing
`os.Stdout` directly. That is what makes every command testable without a real terminal, and
what will let the terminal shell drive these same commands as library calls later instead of
shelling out to itself.

## Decisions worth recording

**This package holds no deletion logic of its own.** Every command is a thin translation from
arguments into a call against the deletion engine, protection rules, and operation log. The
single funnel the engine promises only holds if every entry point actually uses it rather than
reimplementing a shortcut, and a command layer is exactly where that temptation shows up first.

**A purge requires typing the word "permanently," not a single keystroke.** A staged removal can
be undone, so a quick `y` is proportionate friction. A purge cannot be undone, and deserves more
friction than the same keystroke that answers every other yes-or-no prompt in the tool,
including one a person's finger might already be moving toward from a previous confirmation.

**A non-interactive session refuses to proceed without `--yes`, unconditionally.** Prompting
into a pipe would block forever waiting for an answer nothing will send. `--yes` in that
context is deliberate: the flag is the explicit, scriptable confirmation a real terminal session
gets by typing an answer.

**Standard library only, no argument parsing dependency.** The command surface is three
subcommands with a handful of flags each. Adding a framework for that is the opposite of the
single static binary, no runtime dependency goal this project already stated as a value.

## Red team findings

**One: a batch id from the command line was treated as trusted input.** The first version of
`undo` joined the user supplied batch id directly onto the staging root and opened whatever that
produced. A batch id is generated by the staging area as a timestamp and a hex suffix, and the
comment beside the join said as much, but the id reaching that line had come from `os.Args`, not
from the staging area. `wtff undo ../../../etc` would have joined outside the staging root
entirely. The comment described what the value was supposed to be, not what it was, and nobody
had checked which one was actually true. Fixed by validating the id against the exact pattern
the staging area generates before it is used in any path, checked against the compiled binary
with the literal traversal string, not only against a test.

**Two: `filepath.Abs` collapses a parent reference lexically before path validation ever runs.**
Path validation rejects a caller supplied ".." outright. That rejection could never fire for
anything typed at the CLI, because by the time a candidate reached it, `filepath.Abs` had
already turned `../../etc/passwd` into wherever that resolved to. This was not a containment
break: whatever the collapsed path turned out to be was still fully validated by the structural
floor and protection rules, exactly like any other path. What broke was the same principle
decision 0006 already named once: a tool whose premise is that a person can trust what they are
shown must not silently substitute a different target for a typo instead of explaining it. Fixed
by rejecting a caller supplied parent reference explicitly, before any function that cleans the
path runs.

That fix was wrong on its first attempt, and the way it was wrong is worth recording. The check
was placed after `expandHome`, and `expandHome` calls `filepath.Join` internally, which cleans
its own result the same way `filepath.Abs` does. `~/../../etc/passwd` was already collapsed to
`/etc/passwd` inside `expandHome` before the new check ever saw it, so a traversal hidden behind
a leading tilde sailed through the fix meant to catch it. Found by writing the second test rather
than trusting that a fix proven against one caller held for another, and by checking what
`expandHome` actually does rather than what its name suggests. The check now runs on the raw
argument before either function touches it, which is the only point in the sequence where
nothing has cleaned the string yet.

## Verification

Two hundred and thirty two tests passing across the tree, `go vet` clean, `gofmt` clean.

The CLI suite drives every command through the public `Run` entrypoint rather than calling
internal functions directly, including a full stage, list, undo round trip that reads restored
file contents back rather than only checking exit codes. Both traversal vectors, a raw `..` and
one hidden behind a tilde, are pinned as separate cases, since the second was missed by the
first case's own fix.

The stack was also exercised through the compiled binary directly, not only through `go test`:
a real stage and undo cycle with content verified, a non-interactive refusal, a protected
keychain path skipped with its reason printed, a batch id path traversal attempt rejected, and
both collapsed-traversal arguments rejected with the exit code and message checked by hand.

## Known limitations

There is no `--json` output yet, so `remove`, `undo`, and `staged` are not yet scriptable in the
structured-output sense the project's own automation value implies. Recorded as future work
rather than half built now.

The `remove` command accepts arbitrary paths named directly on the command line. It has no
concept of a cache category or an app to uninstall; that is what the `clean` rule catalog and
`uninstall` discovery are for, and neither exists yet. `remove` is the general purpose primitive
underneath both, and is usable on its own for the one thing it was built to prove: that the
safety core is actually reachable from a terminal.

## How this could improve with time

Add `--json` to `remove` and `staged` once a real caller needs it, rather than speculatively.
Consider whether the purge confirmation word should also be required from a script that passes
`--yes --purge` together, or whether that combination is legitimately the more deliberate,
already-explicit path a script takes; the current behavior treats it as the latter and this
should be revisited if a real incident suggests otherwise.
